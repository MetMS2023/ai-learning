LLM Training, RL Rollouts, and Training–Inference Integration

This note maps the full LLM lifecycle from pre-training and post-training to production serving. It focuses on why on-policy RL requires fresh rollouts, where PPO and GRPO fit, and what training–inference integration actually solves.

Core idea: the current policy generates rollouts, updates its weights, and then generates the next batch of experience. That is standard on-policy RL; the distinctive LLM challenge is executing generation, scoring, training, and weight synchronization efficiently at massive scale.

01

The LLM lifecycle: from training to deployment

Let us start with the big picture. Using the most familiar terms, this note summarizes post-training as SFT, RLHF, and RL. These are not three mutually exclusive boxes with perfectly sharp boundaries.

Pre-trainingLearn language and knowledge patterns
Post-trainingSFT · RLHF · RL
Evaluation and releaseSelect a checkpoint
Production inferenceSGLang / vLLM
Post-trainingGoal: improve responses, alignment, and task-solving ability
SFT · Supervised fine-tuningShow the model ideal answers and have it imitate them.
RLHF · Alignment from human feedbackUse human-preference signals to shape model behavior; the classic recipe may include a reward model and PPO.
RL · Reinforcement learningThe model first attempts a task, then updates from rules, verifiers, reward models, or environmental feedback.
A note on terminology RLHF commonly uses RL, so the two are not entirely separate or parallel stages. They are listed separately here to make the introductory picture easier to follow: RLHF emphasizes adjusting a model from human preferences; RL emphasizes the attempt → reward → update mechanism. The classic InstructGPT RLHF pipeline is SFT → reward model → PPO.[1]
02

What problems do pre-training, SFT, and RL solve?

2.1 Pre-training: build broad foundational capabilities

For autoregressive language models such as GPT, pre-training typically learns language patterns, knowledge associations, and transferable representations from large corpora of text and code by predicting the next token. It does not write encyclopedia entries into a database one by one; it embeds statistical regularities in model parameters.

My takeaway Pre-training lets the model read widely and learn language regularities, but it does not guarantee instruction-following, formatting discipline, or alignment with human preferences.

2.2 SFT: provide ideal answers for the model to imitate

SFT (supervised fine-tuning) uses prepared “question → ideal answer” examples. During training, model predictions are compared with the target answers, and backpropagation adjusts the weights.

Fixed demonstration dataQuestion + ideal answer
Model imitates the answerPredict the next token
Compute the errorDifference between prediction and target
Update weightsLearn the desired patterns

2.3 Online RL: let the model attempt the task before updating

Online RL has the current model generate answers or action sequences called rollouts (sampled trajectories). The system then assigns rewards based on the results and adjusts the model.

Current modelThe current capability version
Generate rolloutsAnswers, code, or tool-use trajectories
Verification and rewardCorrectness, tests, or preference scores
Update model weightsIncrease the probability of high-reward behavior
The most important basic conceptHere, “updating the policy model” usually means updating the trainable weights of the language model. In RL terminology, a policy describes the probabilities with which the model generates tokens or actions for a given input. Changing the weights changes those output probabilities, so we say the policy has been updated. If only LoRA is trained, the adapter parameters change rather than all base-model weights.
How is a rollout related to ordinary inference? Text generation uses the same forward computation, but RL also stores training information such as generation probabilities and rewards, then performs backpropagation. User-facing production inference usually generates an answer without backpropagating after every request.[2]
MethodWhat the model receivesHow the model learns
Pre-trainingLarge corpora of text, code, and other dataLearn next-token prediction

03

On-policy RL requires fresh rollouts

“Online” does not mean connected to the internet. Here we are discussing common on-policy RL: the current policy generates fresh answers or actions, those experiences provide the training signal, the weights are updated, and the updated policy generates the next batch. This is the standard on-policy RL mechanism, not an algorithm unique to LLMs.

Model θ₀Generate the first batch of experience
Update weights from rewardsObtain θ₁
Model θ₁Generate the second batch of experience
Continue updating weightsObtain θ₂…
A student-practice analogy Each time a student learns something, they attempt the next set of problems at their new level. New answers produce new feedback, which changes the student again. Likewise, θ₀ generates experience and is updated into θ₁; θ₁ then generates the next batch. PPO and GRPO are typical algorithms that turn rewards into these weight updates.
04

PPO and GRPO: turning rewards into weight updates

The model has generated rollouts and received rewards. The next question is: which answers should be reinforced, and by how much should the weights change? PPO and GRPO are two algorithms for this stage.

Generate answersThe model attempts the task
Receive rewardsEvaluate answer quality
PPO / GRPOConvert rewards into a training signal
Update weightsObtain a new model

The key difference: how do they judge how good an answer is relative to a baseline?

ComparisonPPOGRPO
Basic approachTrain an additional critic to estimate the expected score of an answerGenerate a group of answers to the same problem and compare their scores within the group
IntuitionReinforce the answer when its actual score exceeds the critic’s expectationReinforce an answer when it scores above the group average
Additional costRequires training and storing a criticNo separate critic, but multiple answers must be generated for each problem
Shared propertyBoth require reward signals and update language-model weights through backpropagation

PPO: compare with an expected score

For example, if the critic expects 60 points but the answer earns 85, the result is better than expected, so the model should preserve more of this response behavior.

GRPO: compare within a group

Generate four answers to the same problem. If the group average is 60 and one answer scores 90, that answer is above the group baseline and is reinforced.

Both ultimately do the same thing

Turn the comparison into a training signal and use backpropagation to adjust model weights from θ₁ to θ₂.

Strictly speaking, PPO constrains each update from becoming too large, and the original GRPO design also includes stability constraints. Those mathematical details do not change the core intuition here.[2][3]

Both still require rewards Math answers can be verified and code can be tested; more subjective tasks may use a reward model. GRPO removes the separate critic—not the scoring step.
05

Training–inference integration: making generation and training work efficiently together

Now connect the first four sections: the model first uses Inference to generate rollouts; PPO/GRPO then use Training to update the weights. The new weights return to the inference side to generate the next batch of rollouts. This loop may repeat hundreds or thousands of times.

Inference engineGenerate rollouts at scale
Environment and toolsRun code, search, or take actions
Reward and verificationJudge outcome quality
TrainerPPO / GRPO updates weights
Why not use an ordinary training program? Both SFT and RL training perform a forward pass, compute a loss, and update weights through backpropagation; the key difference is where the examples come from. SFT usually uses prepared demonstrations, whereas on-policy RL must continually sample fresh rollouts from the current policy and repeat “generate → score → update → synchronize new weights.”

That is what training–inference integration addresses: it does not introduce a different RL update principle or conflate training with inference. It makes rollout generation, scoring, training, and weight synchronization efficient at LLM scale.

Inference hands off rollouts

Pass newly generated answers, action trajectories, and associated training information to scoring and training.

Training returns new weights

PPO/GRPO updates the model from rewards and returns the new weights to inference for the next round.

The system reduces idle time

Reduce data movement, repeated loading, and GPU idling so the loop runs faster.

Training and inference may alternate on the same GPUs or run on separate GPU pools. This is an engineering choice, not a change to the core process. HybridFlow and vLLM both support coordination and weight synchronization between training and generation.[4][5]

06

After training: switching from learning mode to serving mode

Once a training run reaches its goals, the team selects candidate checkpoints, evaluates capability, safety, and stability, and hands the chosen weight snapshot to the production inference system.

Complete trainingStop updates for this run
Evaluate checkpointsCapability · safety · stability
Select a weight snapshotChoose the production model version
Deploy with an inference frameworkSGLang / vLLM
Serve usersForward generation only

What does the inference framework do?

Inference frameworks such as SGLang and vLLM no longer aim to teach the model. Their job is to answer more requests faster, more cheaply, and more reliably with the chosen weights. They handle request scheduling, continuous batching, KV cache and GPU-memory management, model parallelism, and optimized kernels. Prefill/decode disaggregation, low precision, and multi-node deployment depend on the configuration.

The complete chain SFT and RL-based post-training methods change model weights. RLHF is a human-feedback alignment paradigm whose classic pipeline can use RL. On-policy RL uses an inference engine to generate fresh rollouts; PPO/GRPO turns rewards into weight updates; and training–inference integration addresses the systems efficiency of this standard loop at LLM scale. After training, the chosen weight snapshot is served by SGLang/vLLM.

Six takeaways

  1. LLMs first undergo pre-training and post-training. SFT, RLHF, and RL are common post-training terms, but they can overlap.
  2. SFT imitates target answers; online RL first generates rollouts, then updates weights from rewards.
  3. For PPO/GRPO, “updating the model” means training its trainable weights.
  4. PPO and GRPO sit between “receive reward” and “update weights,” computing how the weights should change.
  5. Training–inference integration connects rollout generation and training updates, with either colocated or disaggregated deployment.
  6. After training, the selected weight snapshot is served by inference frameworks such as SGLang and vLLM.
