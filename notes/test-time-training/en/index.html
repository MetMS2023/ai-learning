Test-Time Training: Letting LLMs Keep Learning While They Work

The point is not to chase rumors about SSI, but to understand TTT as a research direction that could change the shape of LLMs: why it exists, whether it still uses Transformers, how context is written into weights, and how the model can avoid getting worse as it learns.

Core intuition:Today’s LLMs treat context as temporary scratch space. TTT turns current experience into a small training process so useful information can enter temporary weights.

01

What problem is TTT trying to solve?

The dominant LLM paradigm is to train a fixed set of weights on enormous datasets, then perform only forward computation (inference) after deployment. No matter how long a document the user provides, its information normally remains in the current context or KV cache rather than becoming a new model capability.

Problem A · Context cost

Full attention gets slower as the context grows

To generate each new token, full attention must inspect an ever-growing history of keys and values. The longer the context, the higher the cost of each new token.

Problem B · Sliding-window forgetting

A fixed window is fast, but older content falls out

Sliding-window attention sees only the most recent span, keeping its cost stable. The tradeoff is that tokens outside the window are no longer visible.

Problem C · The model does not learn on the spot

Seeing is not the same as learning

Ordinary inference can temporarily reference a long document, but the model weights do not change from that experience when the conversation ends.

TTT-E2E proposes another way to handle long context: keep a cheap sliding window for recent content while using next-token prediction to keep training the model at test time, compressing information that is about to leave the window into temporary weights.[3]

A long sequence streams inDocuments, code, or history
Sliding windowDirectly inspect recent tokens
TTT gradient updateLearn from the current window
Temporary weight memoryRetain predictive patterns
“Compression” is not verbatim storage. Weights are more like the understanding formed after reading a book than the original pages that can be revisited exactly. Full attention, RAG, or external storage still matters for exact quotations, numbers, and provenance.

Does it still use a Transformer?

Answer: yes, in the 2025 TTT-E2E paper. It keeps the basic Transformer backbone, replaces full attention with sliding-window attention, and allows some MLPs in the final quarter of the blocks to update at test time.[3]

The four basic Transformer components

Embedding · Translator

Turns text tokens into numeric vectors the model can compute with. It defines the model’s basic language coordinate system.

Attention · Retrieval mechanism

Decides which earlier tokens the current token should read from. Here it only inspects the recent sliding window.

Normalization · Stabilizer

Keeps values at a stable scale across layers so signals do not explode or vanish through the network.

MLP · Processor

After attention finds information, the MLP further processes each token’s internal representation. It contains a large amount of writable capacity.

What does the static MLP actually guarantee? It only guarantees that its own parameters are not overwritten by the inner-loop optimizer: Wstatic,new = Wstatic,old. It learns together with the whole model during meta-training and remains a fixed computation path at test time. It is not a complete backup of all knowledge, nor a mathematical guarantee that dynamic updates can never hurt performance.
The dynamic and static MLPs are not independent parallel backups. According to the official code, each final-quarter block passes through the dynamic MLP and then the static standard MLP. Because the dynamic MLP changes the intermediate representation, it indirectly affects the static MLP’s actual input and output.
What is a residual connection? Both dynamic and static MLPs use residual connections: instead of replacing the input completely, the module learns a modification that is added to the original input, namely output = original input + module result. Even if the learned modification is imperfect, the original input retains a direct path.

Why update only the final quarter of blocks?

Updated rangeObservation in the paperMeaning
Final layer or final 1/8Insufficient long-context scalingToo few writable dynamic weights; insufficient temporary memory capacity
Final 1/4Scales well with context lengthA sweet spot between capacity and backward-pass cost
Final 1/2Performance is similar to the final 1/4Updating more layers adds little benefit but requires a longer backward path

Thus, “the final quarter” is not a universal law. It is the tradeoff found by ablation for the models and context lengths in this paper. Embedding, normalization, and attention remain frozen because including them in the inner loop made the outer loop unstable.[3]

Do not collapse different TTT papers into one architecture. The 2024 TTT-Linear/TTT-MLP work turns the hidden state into a small learner. The 2025 TTT-E2E work keeps a sliding-window Transformer and directly updates some of its standard MLPs. They share the test-time-learning principle but use different structures.[2]
03

Inner and outer loops: learning on the spot and meta-learning

First see how the two loops relate, then examine each one.

Outer loopChoose and improve the shared starting point W₀
Inner loop · Document A
W₀ → W₁ᴬ → W₂ᴬ
Inner loop · Document B
W₀ → W₁ᴮ → W₂ᴮ
Inner loop · Document C
W₀ → W₁ᶜ → W₂ᶜ

What does the inner loop do?

Learn within one document, answering: “How should my dynamic weights change for this document?”

What does the outer loop do?

Compare outcomes after inner-loop learning across many documents and improve the shared W₀ so it learns new documents more effectively.

The outer loop is the meta-learning process described here. It does not learn one document during deployment. During model development, it observes the results of many inner loops and improves the initial W₀ shared across documents.
The two loops operate at different stages. During development, the outer loop repeatedly simulates many inner loops. After deployment, the trained W₀ is used to run only the inner loop on the current document. Document A’s temporary W₂ᴬ is not directly carried into an unrelated document B.

Inner loop: how does the model read and update weights at the same time?

A provided text naturally contains its own targets: preceding tokens are the input and the actual next token is the label, so no human annotation is required.

Read a batch of tokensThe window contains real text
ForwardPredict each next token
Loss + backward passCompute error and gradients
Update the dynamic MLPWrite information into temporary weights
  1. Forward: The model reads the batch with its current weights and predicts each next token.
  2. Loss: Compare predictions with actual tokens to obtain cross-entropy loss.
  3. Backward: Compute which dynamic-MLP weights contributed to prediction errors and in which direction they should change.
  4. Optimizer step: Use the gradients to update the dynamic MLP into a state better adapted to the current document.
  5. Next batch: The model uses the new state to process subsequent tokens.

Why does the outer loop need “gradients of gradients”?

Ordinary pre-training only optimizes whether fixed weights predict well; it does not optimize whether the model improves after several inner-loop updates. The outer loss evaluates the updated W₁ and W₂, then traces back to the initial W₀. Exact backpropagation must therefore pass through the inner-loop gradient operations—effectively taking a gradient of a gradient. First-order approximations can also omit some second-order terms.[3]

In one sentence The inner loop learns the current document; the outer loop (meta-learning) learns in advance how to learn better from documents.
04

How are TTT and LoRA related?

First, understand LoRA

Full fine-tuning directly changes a large number of the model’s original weights, making training and storage expensive. LoRA (Low-Rank Adaptation) freezes the original weights W, trains only two small matrices A and B, and adds their update to the original computation.

Base weights WFrozen; not directly modified
Small LoRA matrices A × BTrain only a small number of parameters
W + ΔWBase capability + task adaptation
Why “low-rank”? Instead of training one enormous ΔW directly, LoRA approximates it as the product of two narrow matrices. This greatly reduces the parameters that must be trained and stored.

With LoRA defined, their roles are clearer: TTT determines when learning happens and which data it uses; LoRA is merely one low-cost tool for modifying parameters.

ConceptQuestion it answersCore approach
TTTWhen and why should learning happen?Learn from current data at test or use time to adapt the model to the current instance
LoRAHow can an update use fewer parameters?Freeze original weights and train only additional low-rank matrices

Therefore, TTT can use LoRA, but does not have to. Work such as ARC TTT, qTTT, and Self-Guided TTT uses LoRA to reduce the cost of per-instance adaptation: base weights remain fixed while a small temporary update is stored.[5]

The final TTT-E2E design is not LoRA-based TTT. The TTT-KVB comparison used multi-head MLPs with LoRA. Final TTT-E2E found that because backpropagation itself is already expensive, updating larger standard MLPs in only the final quarter of blocks is more effective than updating many tiny LoRA states. This provides greater memory capacity while shortening the network path traversed by backpropagation.[3]

LoRA approach

The base model is fully frozen and temporary memory lives in small low-rank updates. It is cheap and easy to isolate, but has limited writable capacity.

TTT-E2E approach

Directly update a few larger native MLPs. Each update is more expensive, but the dynamic state has greater capacity.

Shared goal

Restrict the plastic region so the entire model cannot drift arbitrarily on one test input.

Parameter adaptation is broader than LoRA

Shared point None of these parameter files is an independent model. They describe how to modify a particular W₀, so they must record compatibility information such as the base-model version, architecture, target layers, and tokenizer.
05

How can an LLM avoid getting worse after its weights change?

The honest answer: there is no absolute guarantee today. A central challenge in TTT is the plasticity–stability tradeoff: the model must learn from new context without destroying its pre-trained capabilities. The paper uses several safeguards to reduce the risk, but this remains an open research problem.
1

Prepare with meta-learning

The objective directly evaluates performance after TTT instead of assuming any gradient update will help.

2

Update only MLPs

Embedding, normalization, and attention remain frozen; the paper found that updating them caused training instability.

3

Open only the final quarter of blocks

Limit the editable region while retaining enough context-compression capacity in the experiments.

4

Keep a static standard MLP

It learns stable capabilities with the model during meta-training and remains frozen at test time. It provides a fixed computation path, not a complete knowledge backup or a guarantee against harm from dynamic changes.

5

Update by mini-batch

Aggregate gradients over roughly 1K tokens instead of stepping after every token, improving parallelism and reducing accidental gradient explosions.

6

Treat updates as session state

Each sequence starts from a shared initialization so adaptation to one document does not automatically contaminate an unrelated document.

Later work further demonstrates the risk: TTT on random, irrelevant spans of long text can reduce performance, while selecting evidence relevant to the question can improve it. This means that what the model learns is as important as how it learns.[6]

Correct interpretation TTT-E2E does not allow unrestricted self-modification. It predefines the editable region, learning objective, initialization, and update cadence so weight updates function as controlled temporary memory.
06

Why could TTT become a future paradigm?

It changes not a small feature, but the basic assumption of when a model learns.

Context windowKeep information in view without changing weights; good for exact access to recent content.
RAG / external memoryLook up notes when needed; good for facts, provenance, and updatable knowledge bases.
Test-time computeLet a fixed model think for more steps; increases search without writing experience into parameters.
TTTThe model genuinely learns within the current task, compressing context into temporary weights.

In the paper’s experiments, a 3B model using a standard sliding-window Transformer showed context-length scaling similar to full attention and reported about 2.7× lower inference latency at 128K context on an H100. The authors therefore reframe long context as a continual-learning problem, not merely an architecture problem of expanding attention windows.[3]

If this direction matures, LLMs may become more than static knowledge bases queried after training. They could become learning systems with a stable foundation and the ability to form temporary capabilities quickly from current experience.
This is not evidence of SSI’s technical approach. TTT resembles Ilya Sutskever’s public discussion of learning after deployment, but SSI has not released a technical report confirming TTT. This note studies TTT as an independent research paradigm and does not use rumors as evidence.
07

What is still missing before TTT is mature?

Training cost

Meta-learning requires gradients of gradients. The current 8K implementation is about 3.4× slower than standard pre-training; one major reason is that today’s optimized FlashAttention interface cannot differentiate the outer loop through the inner backward pass.[4]

Inference systems

Serving requires more than a forward pass: the system must retain training activations, run backward passes, update weights, and isolate dynamic state for each session.

Safety and data quality

Incorrect, malicious, or irrelevant context can create harmful gradients. The model must decide what is worth learning and what must be ignored.

Exact memory

Compressing experience into weights is lossy. Exact numbers, quotations, and provenance still require attention, RAG, or external storage.

Long-term retention

The paper focuses on temporary learning within one long sequence, not permanent continual learning across users and months.

Validation at scale

The main results reach 3B parameters, 164B training tokens, and 128K context—still far from the largest production models.

What is FlashAttention? It is a low-level GPU algorithm and API for efficient Transformer attention. By computing in tiles, it avoids repeatedly writing the full, enormous attention matrix to GPU memory. The current interface supports ordinary forward and backward passes, but the outer loop cannot differentiate through that backward pass, so TTT-E2E meta-training cannot yet fully benefit from its acceleration.

A possible product form: layered learning state

The following is a product-level inference from existing technology, not a conclusion of the TTT-E2E paper

If within-task TTT becomes mature, products are unlikely to copy a complete base model for every user. A more realistic structure is a shared stable W₀ plus smaller states at different timescales.

Shared layer
Base model W₀
General language, reasoning, and generation capabilities shared across users
Long-term personalization
Organization / user / project parameters
May use LoRA, adapters, or other small weight deltas
Fast learning within a task
TTT dynamic state
Changes throughout the current long task; may be discarded or consolidated afterward
Exact memory
Context / RAG / file store
Preserve source text, numbers, provenance, and auditable learning records

“A model for every user” is more likely to mean an update for every user

Personalization parameters for an organization, user, or project can be stored as small weight files in cloud object storage, a private enterprise environment, or a local device. When a request arrives, the system shares one loaded W₀ and loads the corresponding update by identity. Hot updates can be cached on GPU, while infrequent ones remain in CPU memory, SSD, or object storage.

Shared W₀Only one copy of base weights on GPU
Load a dedicated updateOrganization / user / project
Current-session TTTForm dynamic state within the task
Combine with external memoryComplete the personalized task
Parameter personalization creates model-provider lock-in. LoRA, inserted adapters, and native-weight deltas all depend on a particular W₀’s layer structure and internal representations. An update trained for Model A usually cannot be installed directly on Model B. Even a next-generation model from the same provider may require retraining or distillation.
A truly portable personal asset should include more than an adapter file. The demonstrations, accepted and rejected outputs, project files, memories, and personal evaluation suites that produced the personalized parameters are more valuable long-term. An adapter is like a compiled artifact for a specific W₀. When the base model changes, the original learning records can be used to generate a new adapter.

Eight essential takeaways

  1. TTT aims to let a model learn from the current test input rather than merely inspect it in context.
  2. TTT-E2E still uses a Transformer, replacing full attention with sliding-window attention.
  3. The current text supplies next-token labels; the model uses forward → loss → backward to update dynamic MLPs.
  4. Meta-learning prepares an initial model that improves after test-time updates.
  5. LoRA is a low-cost update tool, not TTT itself. Some TTT methods use LoRA; final TTT-E2E does not.
  6. The paper reduces forgetting risk with localized updates, a mostly frozen network, a fixed MLP path, and mini-batches—but offers no absolute guarantee.
  7. The long-term vision is to turn LLMs from static models into controlled learning systems that form temporary capabilities while in use.
  8. Future personalization may combine a shared W₀, small parameter updates, session TTT, and external memory—but parameter updates remain tied to a specific base model.
